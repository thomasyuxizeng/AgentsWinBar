## Targets
- Per-refresh CPU: `< 0.10 CPU-s`

## Environment and Prerequisite Notes
- **Commit 0 (`Fix: Handle unavailable shell taskbar gracefully at startup`)**: All measurements in this environment run unpackaged (`-p:WindowsPackageType=None`) on an isolated virtual desktop without Explorer's taskbar (`Shell_TrayWnd` absent). Without this guard, `AppWindow.IsShownInSwitchers = false` threw `NotImplementedException` (leaving `MainWindow`'s `DesktopAcrylicController` dangling on exit and causing `0xc0000005`), `_trayIcon.ForceCreate()` threw `InvalidOperationException`, and `SHQueryUserNotificationState` returned `QUNS_BUSY` (hiding the taskbar strip). `WindowZOrder.HideFromSwitchers` (falls back to `WS_EX_TOOLWINDOW`), a `try/catch` around `_trayIcon.ForceCreate()`, and `FindWindow("Shell_TrayWnd", null) != IntPtr.Zero` in `WindowZOrder.IsFullscreenAppActive()` make startup resilient when the shell tray is absent while leaving normal desktop behavior and visuals identical. Also kept `App.LogCrash` in `App.OnLaunched` so startup exceptions are never silent.

## Notes on Remaining Idle Floor & Proposals (Not Implemented to Preserve Visuals/Behavior)
- **Virtual desktop CTF thread (`msctfmonitor.dll`)**: On the isolated `exebox` virtual desktop without `ctfmon.exe`, opening `DashboardAppWindow` (which uses `TextBlock IsTextSelectionEnabled="True"` in `DashboardDiagnosticsPanel` and `DashboardProviderPanel`) activates Windows `TextInput` / `msctfmonitor.dll!DoMsCtfMonitor`, adding `~5-6 CPU-s/h` on its own native thread after Dashboard closes even though the UI thread itself is `0.31 CPU-s/h` and 0 managed/XAML controls survive. Removing `IsTextSelectionEnabled="True"` was intentionally NOT done because it alters user-visible text selection behavior; if measured on a normal desktop session with `ctfmon.exe`, re-check whether `msctfmonitor.dll` stays idle there or if copy-button affordances (visual change proposal) should replace inline text selection in diagnostics.
- **Background cost-log scanning**: When local agent session JSONL logs grow continuously (e.g., active agent sessions), periodic cost log scans dominate the occasional `1.5-1.9 CPU-s` spike vs `0.06-0.09 CPU-s` for pure usage refreshes. Debouncing cost-log watcher notifications further during active heavy writes (behavioral timing change proposal) would reduce refresh CPU variance.
